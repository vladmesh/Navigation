### Acceptance criteria
- [x] No `drawCoordinatesNet`, no `updateCoordinates`, no `maxX -= 50`, no `/8` labels. Evidence: all removed from Drawing/uberpainter.cpp and Drawing/uberpainter.h (diff hunks at uberpainter.cpp:30 and uberpainter.h:71). A grep over the repo finds none of these names in the code.
- [x] The step comes only from `GridMath::niceStep(min(w, h), 10)` and the lines only from `GridMath::gridLines`. Evidence: Drawing/uberpainter.cpp:37, :47-48. UberPainter does no step arithmetic of its own. The one-step margin at :46 is the margin the ADR asks for.
- [x] The grid covers all four edges, including with no objects and with one object. Evidence: Drawing/uberpainter.cpp:35-36 and :46 use the visible area plus one step, and the object bbox is not used. The no-object case draws on top of a broken scene rect that predates this PR (finding 3). Coverage in that case is backed only by the coder's offscreen harness, which I cannot rerun.
- [x] 5 to 10 lines across the short side; the wheel changes the step at once. Evidence: Drawing/uberpainter.cpp:215-216 redraws inside `wheelEvent` without waiting for the timer. Caveat: Decision §1 defines "5 to 10" as span/step in (4, 10], so 4 and 11 visible lines do occur. The coder's harness reports 4 to 11. This is a wording mismatch in the ADR, not a code defect (finding 4).
- [x] Each label sits at its own line and shows that line's value: X at the bottom edge, Y at the left edge, `'f'` format with `labelDecimals`. Evidence: Drawing/uberpainter.cpp:64-84. The anchor is the line's scene coordinate on the bottom edge (X) or left edge (Y). With `ItemIgnoresTransformations` the item's own transform is in device pixels with y pointing down, so `fromTranslate(3, -h - 3)` puts an X label 3 px right of its line and 3 px above the bottom edge. `fromTranslate(3, -h)` puts a Y label directly above its line, 3 px in from the left edge. Under `scale(1,-1)` this is correct. The `-0` guard at :67 is correct. Labels near the edges have cosmetic problems (finding 1).
- [x] Labels are not mirrored, keep the same size at any zoom, and the grid code uses neither `mirrorTransform` nor `transform().m11()`. Evidence: Drawing/uberpainter.cpp:71 sets the flag, and :62 uses a fixed 8 pt font. `mirrorTransform` remains only in the ruler code (:148), which is outside the grid.
- [x] Panning with the mouse and resizing rebuild the grid at once; the ruler labels survive a pan. Evidence: Drawing/uberpainter.cpp:172-177 redraws after the base `mouseMoveEvent`, so after both the manual scroll and the ScrollHandDrag scroll. :219-228 handles resize. The old loop that deleted every `QGraphicsTextItem` is gone. Grid labels are `QGraphicsSimpleTextItem` children of `gridGroup`, and `delete gridGroup` (:32) cannot reach the ruler items, which are top-level scene items. Scroll-bar and keyboard scrolling are not covered (finding 2).
- [x] Redrawing deletes only grid items, nothing is deleted twice after `clear()`, and `sceneMutex` is never locked twice. Evidence below.
  - Ownership: `gridGroup` is created without a parent and handed to the scene by `addItem` (:41-43), so the scene owns it. Children get `gridGroup` as their parent (:54, :56, :68). `delete gridGroup` removes the group from the scene and deletes its children. `updateView` sets the pointer to null right after `clear()` (:234-235), and nothing runs in between.
  - Locking: all callers run on the GUI thread (mainwindow.cpp:51-55 creates the timer and connects it, and `runPainterRun` at :759-762 calls `painter->run()` directly). Inside the locked region of `updateView` (:233-299) there is no `processEvents`, so wheel and mouse events cannot arrive in that region. The only event that can arrive synchronously there is a viewport resize caused by `setSceneRect`. `resizeEvent` handles it with `try_lock`, and Qt documents `tryLock` on a non-recursive mutex as returning false, not deadlocking, when the owning thread calls it again. `centerView()`/`centerOn` run before the lock (:232). `mouseReleaseEvent` → `run()` → `updateView` holds no lock on entry.
- [x] Grid lines lie under tracks and objects, and the pen is cosmetic. Evidence: Drawing/uberpainter.cpp:42 sets the group's zValue to -10. Track ellipses and ruler items are at the default z of 0. :50-52 makes the pen cosmetic with width 0.
- [x] Ship.pro builds on Windows with no new warnings in uberpainter.cpp. Evidence: PR-CI run 2 (6130627), MSVC /W4 reports no warnings for uberpainter.cpp, and the MinGW build plus smoke e2e passed.

### Findings
1. [minor] Drawing/uberpainter.cpp:77-84: labels near the edges get clipped or overlap, and a clipped label can read as a different number.
   - Failure scenario A: a vertical line falls within about 45 px of the right edge. Its label is drawn starting 3 px right of the line, so the viewport cuts it off and the user sees, for example, `51236` instead of `512360`. This breaks "each label equals its line's coordinate" exactly where the user is reading.
   - Failure scenario B: a horizontal line falls within `h` px of the top edge. Its label sits above the line and loses its top half.
   - Failure scenario C: a horizontal line falls within `h + 3` px of the bottom edge while a vertical line is near the left edge. The Y label then lands on the bottom row of X labels, and the two overlap in the bottom-left corner. During a pan this happens regularly.
   - Fix: map each anchor plus its offset to viewport pixels (`mapFromScene(anchor)`). Skip an X label when `px + 3 + boundingRect().width() > viewport()->width()`. Skip a Y label when `py - h < 0`, or when `py > viewport()->height() - h - 3 - 3`, which is the band used by the X labels.
2. [minor] Drawing/uberpainter.cpp:172-177: the grid is redrawn only on mouse pan, wheel and resize. Other ways of scrolling move the view without a redraw.
   - Failure scenario: zoomed in on objects, the scene rect (bbox ± 500 m) is larger than the view, so scroll bars are visible. When the user drags a scroll bar, uses the arrow keys or PageUp/PageDown, the view moves without a redraw. Once the view has moved more than the one-step margin, blank strips stay on screen until the next 1 s timer tick.
   - Fix (a simplification that deletes the special case): override `scrollContentsBy(int dx, int dy)`. Call the base implementation, then use the same `try_lock` plus `drawGrid()` as in `resizeEvent`. Then remove the extra block in `mouseMoveEvent` at :174-177. `try_lock` is needed because `setSceneRect` inside `updateView` can call `scrollContentsBy` synchronously while the lock is held. Alternatively, keep the code as it is and have architect-revision record this as a leftover, since the ADR lists only four call sites.
3. [minor] Drawing/uberpainter.cpp:252: with no objects, the grid is drawn over a broken scene rect that predates this PR.
   - Failure scenario: with no objects, `minX`/`maxX` stay at `DBL_MAX`/`lowest()`, so `(maxX - minX) + 1000` is `-inf`. The scene rect becomes `(DBL_MAX, DBL_MAX, -inf, -inf)`. Qt's `recalculateContentSize` then works from an infinite rect whose `right()` is `-inf + inf`, which is NaN. Inside Qt that means a double-to-int conversion of NaN, which is UB. The scroll bars end up near the int limits, and the "visible area" the grid labels describe comes out of that state, not out of meaningful coordinates. The old code skipped the grid in this state (`if (minX == max) return`). The new code draws in it on purpose, as Decision §2 requires. ADR line 79 forbids touching `setSceneRect` in this task, so this is not a defect of this PR.
   - Fix: architect-revision records a leftover or new task to guard `setSceneRect` when no position passed the filter, for example by keeping the previous scene rect or using a default rect around the view center. The tester should check the empty-state labels on Windows.
4. [minor] docs/adr/0001-coordinate-grid.md:188: the criterion "5 to 10 lines across the short side" cannot be met as worded.
   - Failure scenario: Decision §1 guarantees span/step in (4, 10], so 4 and 11 visible lines both occur. The coder's harness saw exactly that. A tester who counts lines literally will file a false bug.
   - Fix: architect-revision rewords the criterion as "span/step in (4, 10] along the short side (4 to 11 visible lines)". The code needs no change.
